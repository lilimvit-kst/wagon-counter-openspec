# Архитектура и стек

Целевая архитектура из ТЗ; текущие статусы находятся в blocks.json.

## 2 Стек и правила версионирования

### Языки и программы

| Слой | Выбранный стек | Назначение |
| --- | --- | --- |
| ОС хоста | Debian 13 amd64 | Docker, сеть, диски, время, запуск сервисов |
| Контейнер Python | Ubuntu 24.04, Python 3.12 | Единая среда приложения и CPU инференса |
| Логика и API | Python, FastAPI, Pydantic 2 | Контракты, команды, HTTP и WebSocket |
| Хранение Edge | SQLite, WAL, SQLAlchemy 2 | Локальный журнал, состояние, очередь доставки |
| Хранение центра | PostgreSQL 17, SQLAlchemy 2, Alembic | События, проекции, пользователи, отчеты |
| Детекция | YOLO26n, OpenVINO, Ultralytics headless | Обученная модель четырех типов |
| Трекинг | ByteTrack из закрепленного Ultralytics | Связывание наблюдений внутри потока |
| Видео для CV | PyAV и OpenCV headless | Декодирование с метками времени, обработка ROI |
| Видеосервер | MediaMTX | RTSP, WebRTC, запись и воспроизведение |
| Сообщения | Mosquitto 2, MQTT 5, paho-mqtt 2 | Доставка событий и команд |
| Веб-интерфейс | TypeScript, React 19, Vite 7 | Три ролевых вида одной платформы |

| Отчеты | ReportLab, openpyxl, модуль csv | PDF, XLSX, CSV с кириллицей |

| OCR опционально | PaddleOCR 3, модель PP-OCRv4, CPU | Отдельное окружение распознавания номера |

C++, CUDA, TensorRT, Kubernetes и отдельный Redis для первой реализации не требуются. Изменение этого решения оформляется после измерения конкретного ограничения.

OpenVINO официально перечисляет Ubuntu 24.04 и Python 3.12 среди поддерживаемых вариантов. Поэтому CV-контейнер использует эту базу. Debian является хостом контейнеров; контейнер не заменяет ядро хоста. Проверка доступности CPU и инференса обязательна на реальном компьютере. [Системные требования OpenVINO](https://docs.openvino.ai/2026/about-openvino/release-notes-openvino/system-requirements.html)

Node.js 24 выбран как ветка LTS; Vite используется только при разработке и сборке. В эксплуатации Nginx или Edge отдает собранную статику. [Выпуски Node.js](https://nodejs.org/en/about/previous-releases), [требования Vite](https://vite.dev/guide/)

### Базовые версии и фиксация зависимостей

Для первого испытания CV использовать OpenVINO 2026.3.1, ultralytics-opencv-headless 8.4.146, CPU-сборку PyTorch 2.9.1 и torchvision 0.24.1. Это исходный набор для проверки совместимости, а не заявление о выполненном испытании. MediaMTX — 1.21.0.

Релизы проверены по первичным источникам: [OpenVINO на PyPI](https://pypi.org/project/openvino/), [Ultralytics headless на PyPI](https://pypi.org/project/ultralytics-opencv-headless/), [пары версий PyTorch](https://pytorch.org/get-started/previous-versions/), [выпуски MediaMTX](https://github.com/bluenviron/mediamtx/releases).

В блоке B01 сформировать отдельные locks/backend.txt, locks/vision.txt, locks/ocr.txt и web/package-lock.json. В locks/vision.txt должны сохраняться CPU-источник PyTorch и точные версии транзитивных зависимостей. Для каждого контейнера записать полный digest. Производственный compose.release.yml использует digest, без latest и плавающих тегов.

Проверка набора включает импорт библиотек, экспорт контрольной модели, одинаковую карту классов, инференс видео, трекинг и тесты контрактов. Если возникает несовместимость, изменить версию через ADR и заново зафиксировать весь набор. Автоматическая установка пакетов или скачивание весов при запуске рабочего сервиса запрещены.

Не устанавливать одновременно opencv-python и opencv-python-headless. Headless-вариант Ultralytics сохраняет модуль импорта ultralytics и пригоден для контейнеров без GUI. OCR получает отдельное окружение, чтобы его зависимости не меняли CV-сервис. [Установка Ultralytics](https://docs.ultralytics.com/quickstart/)

## 3 Архитектура и ответственность сервисов

### Сервисы одной точки

| Сервис | Вход | Ответственность и выход |
| --- | --- | --- |
| mediamtx | Два RTSP потока камер | Ретрансляция, сырой архив, WebRTC и VOD |
| vision | Кадры count-top и fill-angle | Детекции, треки, качество, наблюдения для Edge |
| edge | Наблюдения и команды | Единственный владелец счета; SQLite; локальный API и UI; синхронизация |
| mosquitto | События и команды MQTT | Доставка с QoS 1; не является учетной БД |
| api | HTTP, MQTT-события Edge | PostgreSQL, проекции, RBAC, команды для Edge, UI API |
| worker | jobs и ERP outbox | Отчеты, интеграция, повторные попытки |
| nginx | HTTPS от браузеров | Статика, прокси api и защищенных видеомаршрутов |
| ocr | Выбранные кадры с номером | Кандидаты OCR; включается отдельным профилем |

На одном ПК применять одну внутреннюю Docker-сеть. PostgreSQL, MQTT и служебные HTTP-порты не публиковать во внешнюю сеть. При выносе центра MQTT переводится на TLS, у каждой точки свой пользователь и ACL.

Сервис api запускается одним процессом в пилоте; его MQTT-потребитель является управляемой фоновой задачей жизненного цикла. Переход на несколько API workers требует вынесения потребителя в отдельный singleton-процесс или его явного лидерства. Идемпотентность БД обязательна при любом числе потребителей.

### Границы владения данными

Edge — единственный процесс, который пишет учетную SQLite. Запустить один процесс edge и одну последовательную очередь обработки наблюдений и команд. Дополнительно блокировать второй экземпляр файловой блокировкой. Uvicorn workers для edge всегда равен одному.

Vision не открывает SQLite. Он отправляет ObservationBatch по внутреннему HTTP и повторяет тот же пакет до прикладного подтверждения. Подтверждение Edge означает commit локальной транзакции. Неотправленные пакеты держатся в ограниченной очереди; переполнение или перезапуск фиксируются как разрыв наблюдений и требуют проверки соответствующего интервала.

Центр не редактирует счет напрямую. Ручное действие из центрального UI проходит как команда на Edge. Пользователь видит «Ожидает применения», пока Edge не подтвердит выполнение. Работа центра, ERP, отчетов и видеопредпросмотра не должна блокировать запись счетного события на Edge.

При размещении всего на одном ПК отказ самого ПК останавливает обе логические части. Работа без центра означает независимость Edge от центральных сервисов и сети, но не защищает от отказа общего питания и диска.

### Структура репозитория

~~~text
wagon-counter/
  pyproject.toml
  src/wagon_counter/
    contracts/       # Pydantic DTO и версии протоколов
    domain/          # FSM, пересечения, reducer, инварианты
    edge/            # SQLite, команды, outbox, локальный API
    vision/          # decode, detector, tracker, quality
    center/          # PostgreSQL, API, MQTT ingest
    integrations/    # ERP, справочники, планы
    reports/         # задания, PDF, XLSX, CSV
    cli.py
  web/src/
    api/generated/   # типы из OpenAPI
    features/        # operator, admin, analytics
    shared/
  schemas/           # JSON Schema и OpenAPI
  migrations/edge/
  migrations/center/
  config/            # примеры без секретов
  models/            # manifests; веса поставляются отдельно
  deploy/            # Dockerfiles, Compose, Nginx, MQTT
  scripts/           # сборка, диагностика, резервирование
  locks/
  tests/
    unit/
    contracts/
    integration/
    replay/
    e2e/
  docs/adr/
  docs/blocks/
~~~

Импорты направлены от адаптеров к contracts и domain. Domain не импортирует FastAPI, OpenCV, MQTT и модели БД. Центральная и локальная проекции используют один чистый reducer событий. API-контракты определяются в Python один раз; TypeScript-типы генерируются из OpenAPI и не переписываются вручную.
