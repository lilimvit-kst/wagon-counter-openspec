# Подробные правила OpenSpec для wagon-counter

Версия 1.0 · 10 сентября 2026. Основание: wagon_counter_software_spec_v1_0.md. Все пути относятся к корню архива проекта.

Это комплект для последующего написания кода: новый локальный Git, OpenSpec1.13.0, инструкции агенту и полные планы B00–B14. Исходное ТЗ сохранено без изменения в docs/source. Прикладное ПО предстоит реализовать.

## 1. Устройство OpenSpec

Используется штатная схема spec-driven. Каждый change содержит proposal.md (зачем), specs/ (поведение), design.md (техническое решение), tasks.md (действия и проверки). Контекст и правила подключены через openspec/config.yaml. [Настройка OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/v1.13.0/docs/customization.md)

В openspec/changes подготовлены 15 продуктовых изменений. В openspec/specs пока находится только поставленная организация разработки. После реализации и проверки блока его требования синхронизируются в main specs при архивировании. Планирование всех блоков заранее обеспечивает совместимость, но не делает все функции реализованными.

Фактические статусы и зависимости — docs/blocks.json. Проверка scripts/check_project.py дополняет OpenSpec и контролирует строгий порядок B00→B14. Она проверяет структуру доказательств, а не истинность заявленных результатов испытаний.

## 2. Источники и согласованность

| Источник | Значение | Изменение |
| --- | --- | --- |
| Новые указания пользователя | Актуальное поручение и уточнения | Отразить в change и ADR при необходимости |
| docs/source/ТЗ | Зафиксированное основание 1.0 | Новая редакция отдельным файлом с обновлением карты/hash |
| openspec/specs | Принятые возможности | Через синхронизацию завершенного изменения |
| openspec/changes | Новое/изменяемое поведение | Согласовать с действующими contracts и потребителями |
| docs/adr | Причины решений | Указать заменяемое решение и последствия |
| AGENTS.md | Короткие правила агента | Поддерживать вместе с подробной инструкцией |
| openspec/config.yaml | Контекст, rules артефактов, operations guidance | Сохранять поддерживаемую YAML структуру |
| docs/blocks.json | Граф и реальный статус | По фактически завершенной работе |
| Код/fixtures/generated schemas | Исполняемые контракты | Менять единым совместимым инкрементом |

При противоречии указать затронутые требования. Рутинный выбор внутренней реализации решать самостоятельно. Если вопрос меняет бизнес-смысл и не решен в доступных данных, выполнить независимую часть и затем уточнить. Не спрашивать повторное разрешение на уже порученный блок или обычный локальный коммит.

Hash исходного ТЗ обнаруживает незаметное редактирование, но не отменяет новые требования пользователя. Не «исправлять» ТЗ для удобства тестов; новое решение фиксировать явно.

## 3. Требования к артефактам

### Proposal

Назвать блок, проблему, наблюдаемый результат, зависимости, разделы ТЗ и затрагиваемые сервисы. В Capabilities использовать точные пути новых и изменяемых возможностей. Перед новой capability проверить main specs и активные планы, чтобы не создать вторую сущность для той же функции.

Например, корректировка счета затрагивает контракт, Edge handler, центральную доставку, UI и аудит. Ее нельзя описать только как кнопку.

### Specs

Обязательные английские заголовки сохраняются, текст по-русски. Requirement имеет SHALL/MUST и устойчивый ID. Каждый Scenario содержит WHEN/THEN и проверяемый исход. В исходном комплекте 53 требования и 108 сценариев; карта — docs/TRACEABILITY.md.

~~~markdown
## ADDED Requirements

### Requirement: WC-B03-R01 — Идемпотентная команда

Система SHALL применять повторную команду не более одного раза.

#### Scenario: WC-B03-R01-S01 — Потерян ответ
- **WHEN** примененная команда повторена с тем же command_id
- **THEN** возвращен сохраненный результат без второй дельты
~~~

Это пример формата; полное требование находится в B03. MODIFIED содержит полный новый текст требования и все сохраняемые сценарии. REMOVED объясняет причину и переход старых данных/потребителей. Для новой capability добавить Purpose. В specs описывать наблюдаемое поведение; названия классов и библиотеки — в design.

ID формата WC-Bxx-Rnn-Snn связывает ТЗ, требование, задачу и тест. При добавлении/переименовании обновить карту. Удалять отрицательные сценарии ради прохождения тестов нельзя.

### Design

Описать входы/выходы, владельца записи, направленность импортов, транзакцию, повтор, timeout, рестарт, миграцию и откат. Для CV — PTS, координаты, скорость обработки, бюджет CPU и метод измерения. Для UI — источник состояния и подтверждение команды.

В каждом design сохранены конкретные файлы и действия соответствующего блока из исходного ТЗ. Уточнение внутренних имен разрешено; смена владельца счета, публичного поля или семантики требует согласованного изменения всех потребителей и ADR.

### Tasks

Каждая задача: - [ ] X.Y действие, результат, способ проверки. Порядок: общие контракты → производитель/потребитель → интеграция → релевантные проверки → отчет. Отметка [x] появляется после подтвержденного результата.

«Файл создан» не доказывает работающую камеру, модель или ERP. При нехватке данных реализовать доступную часть и указать конкретный блокер. Для B09 разрешен принятый ручной режим, для B10 — visible_occupancy; эти режимы должны реально работать и быть описаны в capabilities.

## 4. Единицы и бизнес-правила

| Код | Одно место | Масса | Вложенность |
| --- | --- | --- | --- |
| bag_25 | Мешок 25 кг |25 кг|1|
| bag_50 | Мешок 50 кг |50 кг|1|
| bundle_5kg | Пачка 5 кг×10 |50 кг|10|
| bundle_10kg | Пачка 10 кг×5 |50 кг|5|
| unknown | Подтвержденное место неизвестного типа |null|null|

Пачка увеличивает total_units на 1. Unknown входит в итог; полная nominal_mass_kg при нем равна null. Масса известных мест может быть отдельным показателем. Счет не является взвешиванием. Вложенность закрытой пачки берется из версионированного справочника, а не доказывается камерой.

Сомнительное существование объекта — инцидент, а не автоматический unknown. Неотрицательность по типам и равенство суммы общему счету обязательны. Переклассификация unknown→bag_50 оформляется атомарным событием с −1/+1 и нулевым общим изменением.

A→B дает+1, B→A дает−1, A→B→A→B дает итог+1 и три crossing_id. Track_id не является пожизненной отметкой «уже посчитан». Новый трек в B или предсказание без детекции не подтверждает загрузку.

Гистерезис задается временем и реальными наблюдениями: начальный ориентир ТЗ — три наблюдения и 150 мс. Эти параметры проверяются при максимальной скорости мешков. Нельзя снижением критериев скрывать физически недостаточную частоту наблюдений.

Сессия получает UUID до номера; первые места сохраняются. Номер — строка 8 ASCII-цифр с ведущими нулями. Одна незавершенная сессия на точку. Идентификация, дверь, качество, камера и синхронизация — отдельные признаки, не дополнительные состояния общего автомата.

PAUSED и REVIEW продолжают наблюдения; движение возвращает LOADING. FINALIZED автоматически не открывается. В пилоте завершение подтверждает оператор; auto_finalize включается только после своей приемки.

## 5. Межмодульные контракты

| Сущность | Ключ/версия | Правило |
| --- | --- | --- |
| Наблюдение |camera_id/tracker_epoch/observation_seq|Повтор того же hash — прежний результат; другой hash — конфликт|
| Кадр |stream_epoch/frame_seq/pts_ns|Плановые пропуски кадров не равны потере обработанных пакетов|
| Событие |event_id;edge_id/journal_id/sequence_no|Неизменяемость и уникальность в центре|
| Команда |command_id/expected_control_version|Дедупликация до проверки устаревшей версии|
| Счет |last_event_sequence|Учетная последовательность не заменяет управление|
| Управление |control_version|Меняется при управлении/FSM/ручной правке|
| Результат |session_id/result_revision|Исправление — новая редакция и новый ключ ERP|
| Конфигурация |model_version/config_version|Совпадает у Vision/Edge и не подменяется при активной сессии|

Edge — единственный писатель SQLite, один процесс и очередь. Checkpoint/crossing/event/projection/outbox находятся в одной транзакции. Vision БД не открывает. Центр отправляет команды и не исправляет итог прямым UPDATE.

Центр одной транзакцией сохраняет событие, проекцию и contiguous head. Только затем ACK. PUBACK не позволяет удалить Edge outbox. Доставка 1,3,2 дает сначала ACK1, затем ACK3; hash-конфликт не обычный дубль.

Новая БД после утраты получает новый journal_id. После restore старой копии сверить head с центром до live. Неизвестный head требует процедуры нового журнала и инцидента; нельзя повторно выдавать уже существующие sequence_no.

Actor формирует сервер авторизации, не браузер. Новая просроченная команда отклоняется; повтор уже примененной возвращает исходный результат. Ответ 202 означает queued/принято в обработку, не applied.

## 6. Стек, языки и код

Полный выбранный стек и структура папок сохранены в docs/architecture.md. Python3.12 применяется для contracts/domain/Edge/центра/CV/ERP/отчетов; TypeScript — для React; Bash — для коротких процедур окружения. Хост Debian13, Python-контейнер Ubuntu24.04. Node24 нужен инструментам и сборке, в рабочий Edge он не включается.

Domain зависит от contracts и стандартной библиотеки. FastAPI, SQLAlchemy, OpenCV и MQTT — внешние адаптеры. Центр и Edge используют один чистый reducer. UI не владеет счетом.

Pydantic — единственный источник DTO; JSON Schema/OpenAPI/TypeScript генерируются. Изменение формы или смысла поля сопровождается fixtures, потребителями, версиями и миграцией. Параллельные ручные определения Event в Python и TS запрещены.

Ошибки имеют code/message/details/correlation_id. Версия, размеры и поля проверяются до записи. WebSocket после разрыва восстанавливается snapshot. Имена кода/API английские, пользовательские тексты русские.

Backend, Vision, OCR и web build имеют отдельные зависимости. Не смешивать GUI/headless OpenCV. Базовые CV-версии ТЗ — кандидаты B01, не доказанный совместимый набор. Проверить импорт, экспорт, CPU inference и карту классов; затем сохранить locks/источники/digest/лицензии. Автоустановка пакетов/весов при рабочем запуске запрещена.

OpenSpec — инструмент разработки, а не сервер приложения. Наличие npm run check сейчас не означает тестирование еще не написанного backend.

## 7. Камеры и ресурсные ограничения

Камеры передают 1920×1080/30; начальные цели анализа —10–15FPS сверху и 1–2FPS наклонной камеры. Прием/декодирование/архив/UI входят в общий бюджет CPU. Окончательный ПК не выбран; нельзя обещать достаточность процессора без полного теста.

Ограничивать очереди и возраст кадров. Неотправленный ObservationBatch повторять до commit Edge. Потеря очереди/epoch дает инцидент интервала. При перегрузке ограничивать OCR/preview прежде счетного потока; потерю наблюдений не выдавать за непрерывный точный учет.

Архив сырой, оверлей отдельно. BBox/track_id/confidence относятся к тому же обработанному кадру; браузерный overlay поверх WebRTC требует доказанной синхронизации. Последние координаты нельзя рисовать на произвольном кадре. Задержка 200 мс — отдельная измеряемая цель.

YOLO26n/OpenVINO/ByteTrack — начальный адаптер. NMS-free не гарантирует разделение всех соседних мест. Проверять реальные переходы, возвраты и классы; предобученная общая модель не заменяет модель мешков. Train/test разделяются по сессиям, тест не используется для настройки INT8/порогов.

OCR использует видимый ROI одной из двух камер; согласует независимые кадры и формат. Конфликт/таймаут передается оператору. Потеря кадров не закрывает дверь. Угол 15° без системы отсчета и геометрии не дает объем.

FillEstimator возвращает method, visible_occupancy_ratio, volume_m3, volume_fill_ratio, confidence, coverage_ratio, calibration_id, observed_at, unavailable_reason. План, видимая занятость и физический объем раздельны. Без метрической приемки объемные поля null.

## 8. UI, безопасность и ERP

Одна React база дает три ролевых представления по серверным правам и назначенным точкам. Скрытая кнопка не заменяет 403. Форма правки сохраняет command_id при повторе, требует тип/причину и показывает успех после applied.

Локальный UI отдается Edge по независимому TLS8443 и работает без центральных api/PostgreSQL/MQTT/Nginx. Отдельный аварийный пользователь с Argon2id имеет явный аудит. Локальные команды проходят ту же бизнес-валидацию.

Видео защищено отдельно от страницы: camera/action/expiry/права билета. Секреты RTSP/MQTT/ERP не входят в Git, API и логи. БД, видео, веса и датасеты не коммитятся.

Аналитика использует последнюю утвержденную редакцию и сохраняет старые. Снимок плана и timezone воспроизводимы. Confidence без эталона не является измеренной точностью. Сводка, drill-down и экспорты совпадают.

ERP экспортирует полный сверенный watermark через outbox. session_id/result_revision — ключ. Timeout-after-accept разрешается Idempotency-Key или поиском документа; если нет обоих — сверка. FakeERP работает через те же интерфейсы и не имитирует фактическую интеграцию.

## 9. Рабочий цикл одного блока

1. Проверить git status, прочитать правила, текущие спецификации, артефакты change и отчеты зависимостей; сохранить чужие незакоммиченные изменения.
2. Проверить --can-start Bxx. Существующий change не создавать заново. Создать подходящую ветку feat/bxx-тема либо продолжить уже выбранную.
3. Установить in_progress. Уточнить контракты и fixtures, затем реализовать задачи и интеграцию.
4. Проверять наблюдаемое поведение: счетные повторы/возвраты/сбои транзакций; UI через API; схемы через генерацию. Не писать тесты только на наличие своего кода.
5. Заполнить отчет: файлы, версии, команды, условия, ожидаемые/фактические результаты, ограничения, миграция/откат. Каждый Scenario связать с тестом или протоколом.
6. Зафиксировать проверенный код коммитом; полный hash внести в verification.code_commit. Не выдумывать hash будущего коммита.
7. Завершить проверенные задачи, заполнить verification, установить verified и выполнить npm run check. Непройденные критерии оставляют блок незавершенным.
8. Архивировать change с синхронизацией specs, повторить проверку и зафиксировать metadata/архив коммитом. Затем переходить к следующему блоку в пределах поручения.

## 10. Доказательства готовности

Статусы blocks.json: planned, in_progress, blocked, verified. Одновременно один основной блок in_progress. --can-start проверяет все предыдущие, их verified и архивирование. Это проектное правило поверх OpenSpec, не встроенный планировщик CLI.

Verification заполняется после выполнения:

| Поле | Содержимое |
| --- | --- |
|code_commit|Полный 40-символьный hash проверенного кода|
|accepted_mode|Фактический принятый режим, например manual_identity|
|limitations|Массив известных ограничений|
|commands|Массив объектов command,exit_code:0,evidence_file|
|scenarios|По каждому Scenario ID: kind,result,evidence_file|

kind=automated/manual; result=pass. evidence_file — существующий относительный путь внутри проекта с обезличенным протоколом. Один файл может охватывать несколько сценариев, но различает их результаты. Исходное видео/модель идентифицируются hash и поставляются вне Git.

Проверяющий скрипт не исполняет команды из JSON и не доказывает подлинность отчета. Реальные тесты необходимо выполнить, результаты рецензировать. Отметка verified не заменяет эти действия.

Цели ТЗ до ручных правок: precision/recall≥99,5%, тип≥99%, ошибка≤max(1,ceil(0,002×N)). Исходная выборка минимум 10000 перемещений и 20 сессий; OCR при включении минимум 200 эпизодов, ни одной неверной автопривязки на тесте и охват читаемых номеров от 95%. Ресурсный тест минимум 2 часа с обеими камерами, записью и UI. Цели и измерения не смешивать.

## 11. Запуск инструментов и Codex

Нужны Node.js24.x, Git и Python≥3.9 для инструментов; прикладной Python3.12 в контейнерах относится к B01. Node можно установить из [официального дистрибутива](https://nodejs.org/en/download), выбрав Linux x64 ветки 24 и проверив SHASUMS. Уже установленный Node24 менять не требуется.

На Debian подготовить базовые утилиты:

~~~bash
sudo apt update
sudo apt install -y git python3 ca-certificates curl xz-utils
node --version
npm --version
python3 --version
~~~

Из корня распакованного проекта:

~~~bash
bash scripts/bootstrap_openspec.sh
python3 -m unittest discover -s tests/tooling -v
python3 scripts/check_project.py --can-start B00
bash scripts/with-tools.sh openspec status --change b00-contracts-foundation
bash scripts/with-tools.sh openspec instructions apply --change b00-contracts-foundation --json
bash scripts/with-tools.sh codex
~~~

Bootstrap устанавливает закрепленный OpenSpec через npm ci, не глобальную latest. Wrapper добавляет локальный openspec в PATH агента. Последняя команда предполагает установленный/авторизованный Codex CLI. Его авторизацию комплект не меняет. После установки штатных skills открыть новую сессию агента. [CLI OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/v1.13.0/docs/cli.md)

В чат Codex, а не Bash:

~~~text
Используй $openspec-apply-change для b00-contracts-foundation.
Прочитай AGENTS.md, docs/OPENSPEC_RULES.md и docs/blocks.json.
Проверь --can-start B00 и выполни задачи первого изменения:
DTO, fixtures, JSON Schema/OpenAPI, генерация TypeScript и каркас.
Проверь критерии, заполни docs/blocks/B00.md и verification.
Не переходи к B01 в этом поручении. Заверши проверенным локальным
коммитом; архивируй изменение только после реальной готовности.
~~~

Instructions выводит план агенту, а код пишет агент. Штатная Codex-интеграция — skills в .agents/skills и обращение $openspec-apply-change. Расширенный verify workflow в core не установлен: тесты выполнять обычными командами из задач, не придумывать отсутствующий slash command. [Поддерживаемые инструменты](https://github.com/Fission-AI/OpenSpec/blob/v1.13.0/docs/supported-tools.md)

Для нового требования использовать отдельный change/propose. Для реально законченного B00 архивирование выполняется командой:

~~~bash
bash scripts/with-tools.sh openspec archive b00-contracts-foundation --yes
npm run check
~~~

Эта команда меняет main specs. Сейчас ее выполнять на продуктовых блоках нельзя: код еще не реализован. Это условие готовности, а не запрос повторного разрешения на уже выполненную задачу.

## 12. Новый Git

ZIP содержит wagon-counter-openspec с собственным .git, веткой main и начальным коммитом. Новый локальный репозиторий уже создан. Он не изменяет старые проекты. Удаленный origin не назначен, поскольку сервер/владелец не указаны.

~~~bash
cd wagon-counter-openspec
git status --short
git log -1 --oneline
git remote -v
~~~

Для новых коммитов задать свое имя/email локально через git config user.name и user.email. Начальный коммит подписан автором Codex, не именем пользователя. Не делать git init внутри старого проекта для создания нового.

Создать пустой приватный репозиторий на выбранном GitHub/GitLab/Gitea без автосоздания README. Затем:

~~~bash
read -r -p 'URL нового пустого репозитория: ' wagon_remote_url
git remote add origin "$wagon_remote_url"
git push -u origin main
~~~

Если origin уже есть — сначала проверить его. Если remote непустой — не использовать force push: объединить истории по согласованному решению либо выбрать пустой репозиторий. Публикация удаленного Git этим комплектом не выполнена; команды подключения подготовлены.

Коммиты небольшие: feat(edge),fix(sync),test(contracts),docs(openspec). Не сбрасывать чужие правки. CI для GitHub Actions поставлен, но его удаленный запуск состоится после подключения GitHub; на другом сервере использовать те же команды своим CI. Полный CI приложения добавляется в B00/B01.

## 13. Обновление и отчет агента

OpenSpec1.13.0 закреплен package-lock. Обновление — отдельная ветка, новая точная версия, lock, штатный update skills, просмотр diff и проверки. Проектные правила не вшиваются в генерируемые upstream skills: они живут в AGENTS/config/этой инструкции.

Результат поручения содержит блок, наблюдаемую функцию, измененные контракты, команды и фактические исходы, ограничения и следующий доступный блок. Пример: B03 дает 8 после 10 входов/2 возвратов,9 после правки и 9 после повтора, сохраняет итог после рестарта и без центра; камеры относятся к следующим блокам.

Планы и заглушки нельзя выдавать за принятую систему. Первым к реализации остается B00.
