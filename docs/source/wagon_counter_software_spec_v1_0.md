# Техническое задание на программную реализацию системы подсчета мешков при загрузке вагонов

Версия 1.0 • 10 сентября 2026 года

Документ для разработчика и инженера внедрения. Основание — общее ТЗ на систему подсчета и уточнение конфигурации: одна точка, две камеры 1920×1080 при 30 кадрах/с, обычный x86 ПК без Jetson.

Реализация строится вокруг локального журнала событий. Локальный сервис точки принимает наблюдения компьютерного зрения, подтверждает пересечения зоны учета и сохраняет изменения счета. Центральные сервисы получают эти события, строят отчеты и передают результаты в ERP. Такое разделение должно сохранять счет при потере связи с центром и исключать повторное применение доставленного события.

Документ определяет состав программ, контракты, правила учета, порядок написания кода, установку среды и проверки готовности. Производительность моделей и точность оценки заполнения подтверждаются на выбранном ПК и видео с площадки.

## 1 Границы реализации и исходные параметры

### Конфигурация пилота

| Параметр | Требование |
| --- | --- |
| Точки загрузки | Одна; идентификатор point-01 |
| Камера count-top | 1920×1080, 30 кадров/с; вид сверху на контролируемый проход |
| Камера fill-angle | 1920×1080, 30 кадров/с; наклон около 15 градусов |
| Обработка | x86-64 ПК; базовый режим инференса на CPU |
| Ориентир для стенда | Intel Core i5-12400 или сопоставимый ПК; 16 ГБ RAM, SSD NVMe 1 ТБ |
| Сеть | Ethernet; адреса камер закреплены; камеры доступны только из разрешенной сети |
| Размещение сервисов | В пилоте Edge и центр на одном ПК; впоследствии центр можно вынести |
| Идентификация | Ручной ввод доступен всегда; OCR включается после проверки видимости номера |

Указанный ПК — ориентир для испытания, окончательная модель компьютера еще не выбрана. Работа двух потоков сама по себе не доказывает достаточность CPU для детекции, архива и интерфейса одновременно. Угол второй камеры задается вместе с системой отсчета: от вертикали или от горизонтали. До обследования это поле остается неопределенным.

### Состав первой поставки

Обязательны учет четырех типов грузовых мест, сессии с номером вагона, возвраты, журнал ручных действий, работа без центра, операторский интерфейс, видеоархив, административная диагностика, отчеты и адаптер ERP. OCR и автоматическое определение дверей подключаются через предусмотренные интерфейсы после проверки ракурса и качества моделей.

Оценка видимого заполнения входит в программную реализацию. Значения физического объема в м³ и доли занятого объема появляются только после разработки и приемки калиброванного метода. Неопределенный объем отображается как «Нет оценки», без подстановки нуля.

### Единицы учета

| Код типа | Что считается одним местом | Масса места | Вложенных единиц |
| --- | --- | --- | --- |
| bag_25 | Один мешок 25 кг | 25 кг | 1 |
| bag_50 | Один мешок 50 кг | 50 кг | 1 |
| bundle_5kg | Пачка 5 кг × 10 шт. | 50 кг | 10 |
| bundle_10kg | Пачка 10 кг × 5 шт. | 50 кг | 5 |
| unknown | Подтвержденное место с неизвестным типом | Не определена | Не определено |

Для модели закрепить отображение классов: 0 → bag_25, 1 → bag_50, 2 → bundle_5kg, 3 → bundle_10kg. Код unknown является состоянием результата классификации, а не автоматически добавленным пятым классом модели.

Общее количество — сумма мест всех пяти категорий с учетом возвратов. Пачка увеличивает счет на одно место. Камера не подтверждает число мешков внутри закрытой пачки; вложенность берется из справочника SKU.

Масса вычисляется по номиналам типов. При наличии unknown полная расчетная масса равна null; отдельно разрешено показывать массу распознанных мест и число неизвестных. Масса по счету не является результатом взвешивания.

Выполнение плана рассчитывается по количеству мест. Видимая занятость кадра и физическое заполнение вагона имеют отдельные поля и подписи. При нулевом или отсутствующем плане процент выполнения равен null.

## 3 Архитектура и ответственность сервисов

### Сервисы одной точки

| Сервис | Вход | Ответственность и выход |
| --- | --- | --- |
| mediamtx | Два RTSP потока камер | Ретрансляция, сырой архив, WebRTC и VOD |
| vision | Кадры count-top и fill-angle | Детекции, треки, качество, наблюдения для Edge |
| edge | Наблюдения и команды | Единственный владелец счета; SQLite; локальный API и UI; синхронизация |
| mosquitto | События и команды MQTT | Доставка с QoS 1; не является учетной БД |
| api | HTTP, MQTT-события Edge | PostgreSQL, проекции, RBAC, команды для Edge, UI API |
| worker | jobs и ERP outbox | Отчеты, интеграция, повторные попытки |
| nginx | HTTPS от браузеров | Статика, прокси api и защищенных видеомаршрутов |
| ocr | Выбранные кадры с номером | Кандидаты OCR; включается отдельным профилем |

На одном ПК применять одну внутреннюю Docker-сеть. PostgreSQL, MQTT и служебные HTTP-порты не публиковать во внешнюю сеть. При выносе центра MQTT переводится на TLS, у каждой точки свой пользователь и ACL.

Сервис api запускается одним процессом в пилоте; его MQTT-потребитель является управляемой фоновой задачей жизненного цикла. Переход на несколько API workers требует вынесения потребителя в отдельный singleton-процесс или его явного лидерства. Идемпотентность БД обязательна при любом числе потребителей.

### Границы владения данными

Edge — единственный процесс, который пишет учетную SQLite. Запустить один процесс edge и одну последовательную очередь обработки наблюдений и команд. Дополнительно блокировать второй экземпляр файловой блокировкой. Uvicorn workers для edge всегда равен одному.

Vision не открывает SQLite. Он отправляет ObservationBatch по внутреннему HTTP и повторяет тот же пакет до прикладного подтверждения. Подтверждение Edge означает commit локальной транзакции. Неотправленные пакеты держатся в ограниченной очереди; переполнение или перезапуск фиксируются как разрыв наблюдений и требуют проверки соответствующего интервала.

Центр не редактирует счет напрямую. Ручное действие из центрального UI проходит как команда на Edge. Пользователь видит «Ожидает применения», пока Edge не подтвердит выполнение. Работа центра, ERP, отчетов и видеопредпросмотра не должна блокировать запись счетного события на Edge.

При размещении всего на одном ПК отказ самого ПК останавливает обе логические части. Работа без центра означает независимость Edge от центральных сервисов и сети, но не защищает от отказа общего питания и диска.

## 4 Учет и жизненный цикл сессии

### Состояния сессии

| Состояние | Условие входа | Учет и выход |
| --- | --- | --- |
| IDLE | Нет активной сессии | Следить за появлением вагона и движением; создать сессию |
| IDENTIFYING | Вагон появился или оператор начал сессию | Сохранять предварительный счет; получить номер |
| LOADING | Сессия активна и идет перенос | Подтверждать прямые и обратные пересечения |
| PAUSED | Нет переноса дольше idle_timeout | Продолжать наблюдение; при переносе вернуться в LOADING |
| REVIEW | Закрытие дверей после выдержки либо команда завершения | Сверка номера, разрывов, unknown, счета и плана |
| FINALIZED | Условия финализации выполнены | Зафиксировать снимок результата и его revision |

Отсутствие номера не должно терять первые мешки. Сессия получает UUID сразу, wagon_id остается null до подтверждения. Идентичность имеет отдельный статус pending, manual_confirmed, ocr_confirmed или conflict.

Состояние двери — отдельный признак open, closed, partial или unknown. Статусы камеры, качества счета, заполнения и синхронизации также не включаются в перечисление состояний сессии. Это позволяет отличать паузу загрузки от неисправности.

Стартовые параметры для настройки: idle_timeout 30 с, подтверждение закрытой двери 10 с, устаревание признака двери 2 с. Они проверяются по видеозаписям. Потеря камеры не эквивалентна закрытой двери.

В PAUSED и REVIEW наблюдение пересечений продолжается. Новое подтвержденное перемещение отменяет готовность к завершению и возвращает сессию в LOADING. В FINALIZED новое движение создает инцидент; прежний результат автоматически не открывается.

Для пилота окончательное подтверждение REVIEW → FINALIZED выполняет оператор. Автоматическую финализацию разрешить флагом только после приемки датчика дверей, таймаутов и условий качества. Принудительное завершение требует причины и показывает все нерешенные отклонения.

### Пересечения и возвраты

Разметить подход A, полосу перехода и зону B внутри вагона. Для каждого реального трека использовать устойчивую опорную точку и гистерезис. Подтвержденная последовательность A → B создает +1; B → A создает −1. Движение A → B → A → B дает итог +1.

Учет разрешен только по наблюдаемым детекциям. Предсказанные трекером позиции при пропуске детекции не подтверждают пересечение. Трек, впервые появившийся внутри B, не означает автоматически загруженный мешок.

Параметры подтверждения задаются длительностью и минимальным числом наблюдений: первоначально не менее трех наблюдений и 150 мс устойчивого нахождения по сторонам перехода. Эти значения проверяются при максимальной скорости переноса. Если объект проходит зону быстрее, геометрию и частоту обработки надо изменить, а не объявлять цель достигнутой.

Один track_id не означает одно счетное событие навсегда. Переходу присваивается crossing_id; трек определяется парой tracker_epoch и track_id. Повторная доставка одного подтвержденного перехода не изменяет итог. При смене ID возле линии и неоднозначном сопоставлении создать инцидент с видео, без догадки о дополнительном месте.

Тип фиксируется агрегированием уверенных наблюдений до пересечения. При недостаточной уверенности счет увеличивается в unknown. Если существование отдельного места сомнительно, создавать событие проверки, а не автоматически unknown. Для возврата использовать тип ранее сопоставленного места; несопоставленный возврат отправлять на проверку.

### Инварианты

- На точке допускается максимум одна незавершенная сессия.
- Количество каждого типа и общий итог не могут стать отрицательными.
- Сумма по типам всегда равна общему количеству мест.
- Повтор события или команды не меняет уже примененный результат.
- Смена типа одного места оформляется двумя дельтами с нулевой суммой.
- Удаление событий, перезапись истории и прямое редактирование итоговых чисел запрещены.
- Финальный результат имеет номер редакции; последующие исправления образуют новую редакцию.
- Неизвестный номер, разрыв наблюдений и неразрешенные инциденты блокируют автоматическую финализацию.

## 5 Контракты модулей

### Общие правила

Все внешние DTO строго типизированы. JSON Schema и OpenAPI хранятся в репозитории. Время — UTC в RFC 3339; локальная часовая зона площадки нужна для отчетов и отображения. UUID передаются строками. Номер вагона — строка из восьми ASCII-цифр с сохранением ведущих нулей.

schema_version — версия содержимого сообщения. Неизвестную старшую версию направлять в карантин и возвращать диагностическую ошибку, не подтверждая применение. Добавление необязательных полей совместимо; смена смысла поля требует новой версии. Размер пакета, длины строк и допустимые значения проверяются до записи.

      "track_id": 42,
      "bbox_xyxy": [530, 220, 810, 510],
      "type_code": "bag_50",
      "confidence": 0.94,
      "matched_this_frame": true
    }
  ]
}
~~~

Координаты передаются в исходных пикселях, после обратного преобразования crop, resize и letterbox. observation_seq непрерывен среди обработанных пакетов одного tracker_epoch. frame_seq может пропускать кадры при плановом снижении 30 до 15 кадров/с; такой пропуск не является сетевой потерей пакета.

Ключ идемпотентности: camera_id, tracker_epoch, observation_seq. Повтор с тем же ключом и другим hash отклоняется. После перезапуска потока создаются новые epoch; запоздалые пакеты закрытого epoch отклоняются. Edge атомарно сохраняет номер принятого пакета, состояние пересечений и созданные события.

Ответ содержит accepted_observation_seq, generated_event_ids и quality_state. Если версия конфигурации расходится, Edge возвращает 409; Vision останавливает счетный поток до загрузки согласованной конфигурации.

### Неизменяемое событие

~~~json
{
  "schema_version": 1,
  "event_id": "42000000-0000-4000-8000-000000000021",
  "edge_id": "edge-01",
  "journal_id": "42000000-0000-4000-8000-000000000001",
  "sequence_no": 21,
  "point_id": "point-01",
  "session_id": "42000000-0000-4000-8000-000000000011",
  "kind": "count.transfer",
  "occurred_at": "2026-09-10T08:15:03.120Z",
  "actor": {"kind": "system", "id": "vision"},
  "model_version": "bags-1",
  "config_version": 3,
  "payload": {
    "crossing_id": "42000000-0000-4000-8000-000000000031",
    "direction": "in",
    "deltas": {"bag_50": 1},
    "evidence_ref": "clip-000031"
  }
}
~~~

journal_id создается при инициализации локального журнала и сохраняется при обычных перезапусках. sequence_no растет внутри этого журнала, включая события всех сессий. После утраты БД нельзя создавать старый journal_id с нумерацией с единицы. Новая БД получает новый журнал и процедуру сверки.

Минимальные виды событий: session.started, wagon.bound, session.state_changed, count.transfer, count.adjusted, count.reclassified, quality.incident, quality.resolved, session.finalized, result.revised. Системные события без сессии допускают session_id = null; счетные требуют session_id.

Корректировка типа unknown → bag_50 имеет deltas = {"unknown": -1, "bag_50": 1}. Ручная правка дополнительно содержит reason, operator_id и command_id. Hash рассчитывается по каноническому JSON без самого поля hash; алгоритм канонизации фиксируется тестовым набором contracts.

### Команды и версии состояния

Команда содержит command_id, point_id, session_id, command_type, expected_control_version, payload и actor. Команды: start_session, bind_wagon, adjust_count, reclassify_count, request_review, finalize_session, revise_result, acknowledge_incident.

Внешний API назначает actor из авторизованной сессии; присланный браузером operator_id не дает прав другого пользователя. Центр добавляет issued_at и expires_at. Просроченная команда отклоняется Edge без применения; начальный TTL ручной команды — 5 минут. При потере центра оператор использует локальный API, а не накапливает устаревающие корректировки.

control_version увеличивается при изменениях управления, номера, ручных правках и переходах FSM. Каждое автоматическое +1 не увеличивает control_version; счет имеет собственный last_event_sequence. Это позволяет проверять конфликт управления без отказа каждой ручной команды на движущемся счете.

При устаревшем expected_control_version вернуть 409 и актуальное состояние. Повтор command_id с тем же содержимым возвращает прежний результат; с другим — конфликт. Проверять идемпотентность до проверки устаревшей версии повторной команды.

result_revision начинается с 1 при финализации. Исправление финального результата требует отдельного права и причины, сохраняет предыдущий снимок и формирует revision + 1. Новый результат отправляется в ERP с отдельным ключом идемпотентности.

### MQTT и прикладное подтверждение

| Топик под wagon/v1/points/point-01/edges/edge-01 | Издатель | Подписчик |
| --- | --- | --- |
| events | Edge | Центр |
| acks | Центр | Edge |
| commands | Центр | Edge |
| command-results | Edge | Центр |
| health | Edge | Центр |

Events, команды и результаты команд используют QoS 1, retain = false. Health допускает retained-снимок с timestamp, TTL и Last Will. Просроченный retained health не означает, что устройство сейчас работает.

В одной SQLite-транзакции записывать событие, локальную проекцию и outbox. Центр одной PostgreSQL-транзакцией сохраняет событие, обновляет проекцию и фиксирует непрерывно принятый sequence_no. После commit он отправляет ACK с edge_id, journal_id и contiguous_sequence_no.

Edge удаляет запись из очереди доставки только по этому ACK. Брокерный PUBACK не заменяет подтверждение учета в центральной БД. QoS 1 допускает повторную доставку, поэтому в PostgreSQL нужны уникальные ограничения event_id и (edge_id, journal_id, sequence_no). [Спецификация MQTT 5](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)

Событие с пропуском последовательности сохранять в inbox, но не включать в окончательную проекцию до получения пропуска. ACK повторять; Edge повторяет неполучившие ACK записи с задержкой и jitter. Несовпадение hash одного события — инцидент, без автоматического выбора одной версии.

Если подтверждение команды потерялось после применения, центр повторяет тот же command_id. Edge возвращает сохраненный результат. Для локальных команд маршрут доставки не меняет бизнес-валидацию.

## 6 Хранение и восстановление

### Локальная SQLite

Таблицы: journal_meta, sessions, events, event_outbox, commands, projection_counts, crossing_states, observation_checkpoints, incidents, local_users, config_versions. Все связи с сессией используют ее UUID, а не только номер вагона.

Включить foreign_keys, WAL и synchronous = FULL; задать busy_timeout. Полный счет восстанавливается повторным применением журнала. Состояние незавершенных пересечений и checkpoint должны иметь ту же транзакционную границу, что созданные события.

Резервирование работающей SQLite выполнять через Online Backup API. Простое копирование только .db при активном WAL недопустимо. Восстановление испытывать на отдельном каталоге, сверяя суммы и sequence_no.

### Центральная PostgreSQL

Таблицы: edge_journals, event_inbox, events, sessions, count_projections, result_revisions, users, roles, user_points, commands, command_results, plans, incidents, media_refs, jobs, report_schedules, erp_outbox, integration_attempts, audit_log.

Хранить исходный payload события и нормализованные поля для поиска. Индексы: point_id + occurred_at, wagon_id, session_id + sequence_no, состояние jobs/outbox. Вагон может иметь несколько загрузок; wagon_id не уникален на всю таблицу sessions.

Центральные агрегаты воспроизводятся из событий и версий справочников. Изменение справочника массы не должно задним числом менять уже утвержденный результат; сохранять использованную версию.

### Миграции и резервные копии

Миграции Edge и центра раздельные. При обновлении Edge сначала остановить Vision и единственного писателя, создать согласованную копию, затем выполнить миграцию и запустить сервис. Центральные миграции запускать отдельной одноразовой командой до старта api и worker.

Начальная политика: ежедневный pg_dump в custom format, ежедневная копия SQLite, конфигурации и manifests; срок хранения 14 дней на другом носителе или сервере. Неподтвержденный Edge outbox не удаляется по сроку. Максимальный размер журнала на 72 часа работы вычисляется по измеренной пиковой частоте событий с двукратным запасом.

После восстановления старой копии сверить head журнала с центром до приема наблюдений. Нельзя повторно использовать sequence_no уже существующих в центре событий. При недоступном центре и неизвестном head требуется новый journal_id и инцидент сверки; загрузку в live без этой процедуры не возобновлять.

## 7 Обработка видео и моделей

### Прием и расписание обработки

Обе камеры передают исходное видео 1920×1080 при 30 кадрах/с. Для совместимости браузеров начальный профиль камеры — H.264, без B-кадров, ключевой кадр примерно раз в секунду; фактический профиль согласовать с поддерживаемым WebRTC-кодеком. Время камер и ПК синхронизировать.

MediaMTX получает поток каждой камеры и делает архив без наложения графики. Vision читает RTSP от MediaMTX. Каждый поток имеет независимое переподключение с backoff, таймаут отсутствия кадров и проверку замороженного изображения.

Начальные цели: count-top — 10–15 обработанных кадров/с, fill-angle — 1–2 кадра/с, OCR — ограниченные серии попыток по событию. Размер входа YOLO — 640 с сохранением геометрии. При мелких объектах тестировать более крупный вход или crop прохода.

У каждого декодера ограниченная очередь с политикой latest frame. Контролировать возраст кадра, а не только FPS. Уменьшение частоты инференса не отменяет стоимость приема и декодирования исходных потоков. Аппаратное декодирование Intel можно включить отдельным профилем после проверки драйверов и измерений.

Начальный порог устаревания счетного кадра — 500 мс; точное значение привязать к скорости объектов. При его превышении ставить quality = degraded, фиксировать интервал и не выдавать непрерывный счет за подтвержденный. Отключение предпросмотра и OCR имеет приоритет перед снижением счетного качества.

### Детектор и трекер

Реализовать интерфейс Detector.detect(frame) → DetectionBatch и Tracker.update(detections, timing) → TrackBatch. Начальный адаптер использует YOLO26n в OpenVINO и ByteTrack; конфигурация явно выбирает bytetrack.yaml. При необходимости сравнить YOLO26s по счетным ошибкам и полной нагрузке ПК.

Применение NMS-free модели не гарантирует разделение перекрытых мешков. Итог проверяется по фактическим пересечениям, возвратам и классам. Смешение одинаковых пачек разных SKU решается данными или подтвержденным режимом однородной партии, а не предположением по размеру.

Порог подачи детекций трекеру согласовать с его нижним порогом: слишком раннее удаление слабых детекций лишит ByteTrack части входа. Временные параметры трекера и гистерезиса учитывать по частоте обработанных кадров; при изменении частоты обновлять их согласованно.

### Данные и обучение

Собрать видео пустого прохода, каждого типа, смешанных потоков, тесного переноса, возвратов, переносчиков, пыли, разного света и остановок. Размечать наружный контур пачки как один объект. Два разметчика разрешают спорные случаи счетного эталона.

Train, validation и test разделять по сессиям и времени съемки. Соседние кадры одной сцены не должны одновременно попадать в обучение и приемочный тест. Калибровку INT8 выполнять на отдельной репрезентативной выборке, не подбирая параметры по приемочному test.

Обучение выполняется на отдельной машине с GPU. На точке запускается готовый экспорт. Общая предобученная yolo26n.pt пригодна для проверки библиотеки, но не заменяет обученную модель мешков.

Manifest модели содержит model_version, SHA-256 файлов, карту классов, размер и порядок каналов входа, способ нормализации, параметры экспорта, версии библиотек, идентификатор датасета и протокол испытания. Edge сохраняет model_version и config_version в событиях. Смена модели во время активной сессии запрещена.

Экспорт OpenVINO предусмотрен официальной интеграцией. В выбранном API параметр nms = false задает NMS-free head, а quantize = 8 используется для INT8 с калибровочными данными. INT8 включать после сравнения счета с исходной точностью. [Экспорт Ultralytics в OpenVINO](https://docs.ultralytics.com/integrations/openvino/)

### OCR и двери

OCR читает только ROI той из двух камер, на которой фактически виден номер. Если подходящего кадра нет, номер вводит оператор. Дополнительная камера не является условием запуска пилота.

PaddleOCR — библиотека, PP-OCRv4 — выбранное семейство модели. Эти версии не следует обозначать одним несуществующим номером пакета. Адаптер OCR возвращает список кандидатов с текстом, confidence, временем и ссылкой на кадр.

Нормализовать разрешенные пробелы, затем проверять ровно восемь цифр. Несколько независимых кадров должны согласоваться; порог confidence подобрать на данных номера вагона. Если два номера конкурируют или истекло окно попыток, выставить conflict/manual_required. Проверка контрольной цифры подключается конфигурацией для применяемой системы нумерации.

Определение дверей работает по ROI и временной устойчивости. Если геометрия камер не позволяет различать дверь, статус unknown остается допустимым, а завершение выполняется оператором. Отсутствие движения и перекрытая нижняя часть кадра не переводят систему автоматически в «Вагон полон».

### Оценка заполнения

FillEstimator возвращает method, visible_occupancy_ratio, volume_m3, volume_fill_ratio, confidence, coverage_ratio, calibration_id, observed_at и unavailable_reason. method принимает disabled, visible_occupancy или calibrated_volume.

Для visible_occupancy разметить полезную область вагона и исключить переносчиков, дверь и проход. Использовать сегментацию или проверенную оценку занятой видимой области. Обязательно показывать, какая часть кузова наблюдаема и какие зоны скрыты.

Монокулярная оценка глубины не дает гарантированной метрической шкалы. Две камеры с разными ракурсами не становятся стереопарой без общей зоны наблюдения, калибровки и синхронизации. Для режима calibrated_volume требуется отдельная методика с геометрией вагона и эталонными измерениями; до ее приемки объемные поля равны null.

### Видеоархив и оверлей

Сохранить перемотку минимум на 10 минут. Стартовая политика полного архива — 7 дней, настраивается по диску и реальному битрейту. При условных 4 Мбит/с на каждую из двух камер получится около 86,4 ГБ/сутки и 604,8 ГБ за 7 суток без запаса и дополнительных файлов. Диск 1 ТБ требует отдельного расчета места под ОС, БД и закрепленные фрагменты.

Каждое счетное событие получает ссылку на временной интервал видео. Спорные эпизоды закрепляются минимум за 15 с до и 15 с после события в отдельном каталоге до очистки циклического архива. Ссылка на еще не записанный хвост сначала имеет статус pending. Отсутствующий фрагмент отображается явно.

В первоначальном Admin допускается сырой поток и отдельная телеметрия. Для точного оверлея реализовать пониженный аннотированный поток из тех же обработанных кадров: например, 960×540 при 10 кадрах/с, BBox, track_id и confidence рисуются до кодирования. Такой поток создается отдельно от исходного архива, включается по запросу и отключается при недостатке CPU.

Браузерный оверлей поверх сырого WebRTC допустим только при доказанном сопоставлении времени кадра и метаданных. Наложение последних полученных координат на произвольный кадр недопустимо. Полная задержка до экрана менее 200 мс остается измеряемой целью; для CPU-предпросмотра без испытаний она не обещается. [Конфигурация MediaMTX](https://mediamtx.org/docs/references/configuration-file)

### Операторский вид

Показывать номер вагона, статус идентификации, текущую сессию, общий счет, разбивку по типам, выполнение плана, качество счета, связь с центром и время последнего обновления.

«Цифровой вагон» — SVG-схема. Если ячейки отражают план, подписывать «Загружено мест к плану». Если отражают оценку видимой занятости — показывать метод и достоверность. Не превращать долю выполнения плана в процент физического объема.

Действия +1 и −1 требуют выбора типа и причины. Форма подтверждения не закрывается как успешно выполненная до applied от Edge. При повторном нажатии использовать прежний command_id. Для изменения типа предусмотрена отдельная команда, без двух независимых кликов.

При потере центрального сервиса локальный адрес точки открывает тот же собранный интерфейс из Edge. Edge хранит отдельную аварийную учетную запись с ограниченными правами, настроенную при вводе точки. Пароль — Argon2id hash; учетная запись и действия явно обозначены в аудите. Локальная работа не зависит от PostgreSQL, MQTT, api и центральной авторизации.

В пилоте Edge самостоятельно обслуживает HTTPS на порту 8443 с сертификатом локального имени. Локальный доступ сохраняется и при остановленном центральном Nginx. Этот порт разрешается только в сети операторов.

### Администраторский вид

Два видеопотока, статус потока и время кадра; включение счетного оверлея; настройка ROI с версией и предпросмотром на записи; журнал смены моделей; очередь инцидентов с привязкой к видео; просмотр сырых и итоговых счетных событий.

Health показывает доступность камер, received FPS, processed FPS, возраст кадра, p50/p95 инференса и всей обработки, RAM, CPU, свободный диск, размер outbox, возраст старейшего неподтвержденного события, состояние записи и синхронизации часов. GPU и его температура отображаются только при наличии соответствующего устройства и датчика.

Ошибки камеры, остановка записи, рост возраста кадров и исчерпание места создают инциденты. Приоритетный счетный процесс не должен ждать загрузки видео в браузере. Одновременное число предпросмотров ограничивается конфигурацией.

### Аналитический вид

Drill-down: месяц → неделя → точка → сессия вагона. Состояние фильтров хранится в URL. Каждая агрегация указывает часовой пояс, интервал, включенные состояния и версию результата. По умолчанию сводные итоги используют только последнюю утвержденную редакцию каждой сессии.

Показывать planned_units, actual_units и difference_units = actual_units − planned_units, отдельно по типам и всего. План сохраняется с plan_id, source_version и временем импорта; изменение плана после загрузки не переписывает исходное сравнение без отметки.

Тепловая карта показывает долю OCR-отказов среди попыток и долю инцидентов счета на число обработанных мест по точке и часу. Низкий confidence без ручного эталона нельзя подписывать «Ошибка ИИ» или «Точность». Сравнение точности доступно только для размеченных проверенных эпизодов.

PDF-акт содержит номер, сессию, точку, начало и завершение, план/факт, типы, номинальную массу, unknown, правки, инциденты и result_revision. XLSX и CSV повторяют значения API. CSV-ячейки пользовательского текста экранировать от формул таблиц; PDF использует встроенный шрифт с кириллицей.

Периодические отчеты создаются по сохраненным настройкам. Уникальность задания — schedule_id и плановое время UTC. Worker забирает jobs через блокировку строки; повтор после сбоя не должен создавать два файла с одним идентификатором отчета.

## 9 ERP и эксплуатационная целостность

### Финальный пакет

~~~json
{
  "schema_version": 1,
  "session_id": "42000000-0000-4000-8000-000000000011",
  "point_id": "point-01",
  "wagon_id": "12345678",
  "result_revision": 1,
  "finalized_at": "2026-09-10T10:20:00Z",
  "total_units": 1195,
  "types_breakdown": {
    "bag_25": 200,
    "bag_50": 995,
    "bundle_5kg": 0,
    "bundle_10kg": 0,
    "unknown": 0
  },
  "nominal_mass_kg": 54750,
  "plan_units": 1200,
  "difference_units": -5,
  "quality_status": "verified",
  "final_sequence_no": 2451
}
~~~

Пример номера иллюстрирует формат и не подтверждает контрольную цифру. Поле total_units означает грузовые места. Если ERP требует старое имя total_bags, адаптер явно отображает его из total_units; значение не умножается на вложенность пачек.

Экспортировать после получения всех событий до final_sequence_no и сверки центральной проекции со снимком Edge. Ключ идемпотентности: session_id + result_revision. Вызов REST выполняется из erp_outbox с таймаутом, backoff и журналом ответа.

При таймауте результат отправки может быть неизвестен. До повторного создания документа ERP должна поддерживать Idempotency-Key либо поиск по внешнему ключу. Если не поддерживает ни одно, неопределенную отправку переводить в ручную сверку. Ответ 202 ERP означает принятие в обработку; завершение подтверждать по согласованному статусу.

Контракт ERP должен определить URL, авторизацию, справочники SKU, получение плана, семантику исправленной редакции, коды ошибок и подтверждение приема. До получения этих данных использовать FakeERP с тем же интерфейсом; адреса и поля конкретной системы не выдумывать.

### Защита и журналирование

HTTPS для центрального и локального веб-доступа; серверные сессии в HttpOnly cookie, SameSite и CSRF-защита для изменений. Пароли пользователей хешировать Argon2id; секреты камер, ERP и MQTT не хранить в Git, не отправлять в браузер и не включать в логи.

Доступ к MediaMTX закрыть отдельно: прикладная авторизация или короткоживущие билеты с ограничением camera_id, path, действия и срока. Не публиковать открытый видеосервер рядом с защищенным UI. Разрешить CORS только адресам платформы. RTSP-учетные данные в обычном HTTP API не возвращать.

Журнал JSON содержит timestamp, level, service, point_id, session_id, event_id/command_id и correlation_id. Аудит ручных действий сохраняется в БД; ротация технических логов не удаляет аудит.

### Недостаток ресурсов и сбои

| Сбой | Требуемая реакция |
| --- | --- |
| Потерян центр или MQTT | Локальный счет продолжается, outbox накапливается, локальный UI доступен |
| Не работает ERP | Сессия финализируется локально, экспорт ожидает повторения |
| Пропали кадры count-top | Инцидент интервала, degraded, запрет автоматического завершения |
| Пропала fill-angle | Счет по верхней камере продолжается, заполнение недоступно |
| Упал vision | Edge сохраняет итог, перезапуск создает новый tracker_epoch |
| Упал edge | Запись восстанавливается из SQLite; интервал потери наблюдений требует сверки |
| Диск архива заполнен | Очистка незакрепленного архива по политике, алерт; резерв БД защищен |
| Диск учета не принимает запись | Ошибка счетного сервиса; нельзя показывать несохраненные изменения как учтенные |
| OCR не распознал номер | Ручная идентификация без потери предварительного счета |

Разделить квоты архива и учетных данных. Начальные пороги свободного места для раздела БД: предупреждение ниже 20%, критический ниже 10%; дополнительно учитывать прогноз времени до заполнения. Эти пороги уточнить по размеру раздела, без автоматического удаления непереданных событий.

Готовность: сумма детализации совпадает со сводкой и экспортом; исправленная редакция учитывается один раз; границы недели и дня корректны для часового пояса площадки; повтор worker после сбоя не создает двойной отчет.

### B13 Интеграция ERP

Реализовать интерфейс ERPAdapter, FakeERP и адаптер согласованной системы. Подключить импорт плана и export_outbox. Настроить правила unknown, отклонений и исправленных редакций.

Готовность: таймаут после фактического приема не создает второй учетный документ; отправляется только результат с полным watermark; revision 2 не стирает аудит revision 1. Неподдерживаемая идемпотентность приводит к сверке, а не бесконечному повторному созданию.

### B14 Выпуск и эксплуатация

Собрать compose.release.yml с digest, migration job, резервным копированием, healthchecks, ограничениями ресурсов и ротацией. Описать запуск, остановку, обновление, восстановление и аварийный локальный вход.

Провести отказные сценарии раздела 12, испытание на выбранном ПК и восстановление на отдельном чистом стенде. Подготовить release-manifest.json с commit, locks, схемами БД, конфигурацией и моделью.

Готовность: оператор и инженер могут выполнить инструкции без ручных изменений кода; сохранены протокол испытаний и ограничения принятого режима. Старая версия приложения не запускается поверх несовместимой новой БД при откате.

Модели детекции текста и распознавания PP-OCRv4 выбрать явно в адаптере и загрузить при подготовке релиза. Их пути и hash сохранить в OCR manifest. Не полагаться на модель по умолчанию текущего пакета: она может относиться к другому поколению. Проверить цифры на реальных кадрах и запуск с отключенной сетью. [Установка PaddleOCR](https://www.paddleocr.ai/main/en/quick_start.html)

### Шаг 11 Установить готовое приложение после B14

Следующие файлы и команды являются обязательными результатами разработки. До их реализации эти команды не исполнят установку продукта. Релиз поставляется с исходниками либо готовыми образами, compose.release.yml, locks, manifests и README.

compose.release.yml должен включать все инфраструктурные и прикладные сервисы; переносить существующие volumes, а не создавать пустые базы под другим именем проекта. Встроенные CLI обязаны поддерживать --help и прекращать выполнение при ошибке конфигурации.

~~~bash
sudo docker compose -f deploy/compose.release.yml config --quiet
sudo docker compose -f deploy/compose.release.yml up -d \
  postgres mosquitto mediamtx

sudo docker compose -f deploy/compose.release.yml run --rm api \
  python -m wagon_counter.cli migrate-center
sudo docker compose -f deploy/compose.release.yml run --rm edge \
  python -m wagon_counter.cli migrate-edge

sudo docker compose -f deploy/compose.release.yml run --rm edge \
  python -m wagon_counter.cli init-edge \
  --config /config/point-01.yaml
sudo docker compose -f deploy/compose.release.yml run --rm -it api \
  python -m wagon_counter.cli create-admin
sudo docker compose -f deploy/compose.release.yml run --rm -it edge \
  python -m wagon_counter.cli create-local-operator

sudo docker compose -f deploy/compose.release.yml up -d \
  edge api worker nginx
sudo docker compose -f deploy/compose.release.yml up -d vision
~~~

init-edge идемпотентен: не сбрасывает существующий journal_id и счет. Пароли create-admin и create-local-operator запрашиваются без вывода. Миграция Edge не запускается параллельно с работающим писателем.

Установить DNS-имена и сертификаты: центральное, например wagon.example.internal, и локальное edge01.example.internal с портом 8443. Это примеры внутренних имен, не готовые адреса. Сертификат должен быть доверен планшетами и телефонами. Проверить HTTPS, WebSocket и WebRTC в реальной сети пользователей.

Релиз должен определять secret-файлы DATABASE_PASSWORD, MQTT_PASSWORD, EDGE_SERVICE_TOKEN и MEDIA_SERVICE_TOKEN с раздельным доступом. Nginx публикует центральный HTTPS 443; Edge публикует свой HTTPS 8443 с независимой конфигурацией сертификата.

### Шаг 12 Проверить запуск и переключить режим

~~~bash
sudo docker compose -f deploy/compose.release.yml ps
sudo docker compose -f deploy/compose.release.yml exec edge \
  python -m wagon_counter.cli doctor --config /config/point-01.yaml
sudo docker compose -f deploy/compose.release.yml exec edge \
  python -m wagon_counter.cli simulate --scenario ten-in-two-out
sudo docker compose -f deploy/compose.release.yml exec api \
  python -m wagon_counter.cli reconcile --point point-01
~~~

doctor проверяет доступность камеры, время, модель и классы, ROI, каталоги, состояние SQLite, версии схем, секреты и способность commit. reconcile сверяет журнал Edge и центральную проекцию, не исправляя расхождения молча.

Порядок ввода: simulator → video_replay → shadow → live. Для каждого режима использовать отдельные data namespace и каталоги/БД либо явный надежный признак среды во всех ключах. Интеграция ERP в первых трех режимах отключена. Симулятор запрещен для рабочего журнала.

Перед live выполнить приемку видео, резервирование, восстановление и сверку счета. Назначить номер точки, реальные ROI и ракурс; включить счет, затем отдельно включить ERP после проверки внешнего контракта.

### Шаг 13 Обновление и откат

Обновление проводить между сессиями. Сначала сохранить резервные копии, commit и manifests текущего релиза. Остановить Vision и Edge, обновить образы, выполнить миграции и doctor, затем replay короткого эталона в тестовом режиме и запустить точку.

Откат включает совместимую БД и конфигурацию. Если после миграции уже появились новые учетные события, простое восстановление старой копии потеряет их. Использовать проверенную обратную миграцию или перенос новых событий с последующей сверкой. Команда docker compose down -v в эксплуатационных инструкциях запрещена: она удаляет volumes.


## 12 Проверки и критерии приемки

### Проверки разработки

| Уровень | Что проверяется | Обязательный результат |
| --- | --- | --- |
| Unit | FSM, пересечения, reducer, валидация команд | Все инварианты и пограничные сценарии |
| Contracts | JSON Schema, OpenAPI, TS, версии | Совместимые примеры и отклонение некорректных |
| Integration | SQLite, PostgreSQL, MQTT, команды | Дубли, пропуски, потеря ACK без искажения счета |
| Replay | Реальные записи с эталоном | Метрики до ручных корректировок |
| UI E2E | Три роли и локальный режим | Рабочие команды и проверка прав |
| Fault | Перезапуск, потеря сети, диск, камера | Правильная деградация и восстановление |
| Installation | Чистый стенд и поставленный релиз | Запуск по инструкции без изменений кода |

Тесты инфраструктуры выполняются в отдельных БД, volumes и MQTT namespace. Сценарии потери диска и питания не выполняются на рабочем журнале. Успешная симуляция не заменяет испытание на реальных мешках.

### Предлагаемые показатели для пилота

Эти значения — цели приемки, а не результаты измерений. Перед испытанием зафиксировать выборку и правила сопоставления событий.

| Показатель | Цель и способ измерения |
| --- | --- |
| Precision счетных пересечений | Не ниже 99,5%; ложные события считаются ошибками |
| Recall счетных пересечений | Не ниже 99,5%; пропущенные события считаются ошибками |
| Ошибка сессии | Не более max(1; ceil(0,002 × N)) мест по модулю |
| Правильный тип места | Не ниже 99% на эталоне; unknown считается нераспознанным |
| OCR при включении | Ни одной неверной автоматической привязки на тесте; охват читаемых номеров от 95% |
| Потеря центра | До 72 часов событий при расчетной пиковой нагрузке; последующая сверка |
| Возобновление синхронизации | Без двойного применения и без пропуска подтвержденных событий |
| Счетный поток | Устойчивая частота, достаточная для максимальной скорости переноса; начальная цель 10–15 FPS |
| Просмотр WebRTC | p95 до 200 мс как отдельная цель при согласованной конфигурации |
| Заполнение | Видимая доля валидируется отдельно; точность м³ пока не установлена |

N — эталонный конечный счет сессии; возвраты дополнительно проверяются как отдельные направленные события. Итоговая ошибка сама по себе недостаточна: один пропуск и одно ложное событие могут взаимно компенсироваться.

Первоначальный объем приемочной выборки: не менее 10 000 перемещений мест и 20 сессий, с представленностью всех четырех типов и сложных условий. Для OCR — минимум 200 эпизодов идентификации, включая нечитаемые и конфликтные. По результатам уточнить достаточность выборки; отсутствие ошибок на ней не означает нулевую вероятность ошибки вообще.

Для сопоставления эталона и события использовать уникальный проход объекта через линию, направление и временное окно. Первоначальное окно ±0,5 с корректируется по синхронизации и скорости; один эталон может соответствовать только одному событию.

Производительность измерять не менее двух часов непрерывной работы с двумя камерами, записью, реальной частотой мешков, открытым UI и фоновыми задачами. Сохранять p50/p95, фактический FPS, возраст кадра, CPU/RAM и тепловой режим. Пропуск кадров из-за перегрузки включать в качество теста.

### Обязательные отказные сценарии

Потеря центра на действующей сессии; повтор всей очереди событий; доставка 1, 3, 2; потеря ACK после commit; потеря ответа на ручную команду; перезапуск Vision возле линии; перезапуск Edge после сохраненного события; несинхронное время; потеря одной камеры; замороженный кадр; заполнение архива; восстановление резервной копии со старым head; исправление уже отправленной редакции ERP.

Для каждого сценария протокол фиксирует исходный счет, действия, ожидаемый итог, фактический итог, созданные инциденты и необходимость вмешательства оператора. Протокол должен различать восстановленные данные и периоды, в которых наблюдений физически не было.

## 13 Комплект поставки и завершение работ

Разработчик передает репозиторий с историей изменений, схемами и миграциями; исходники веб-интерфейса; закрепленные зависимости; Docker images и Compose; модели с manifest; конфигурации без секретов; инструкции установки и восстановления; тесты и протокол приемки; спецификацию ERP; инструкцию оператору и инженеру.

В release-manifest.json фиксируются версия продукта, commit, digest образов, схемы Edge и центра, версия контракта событий, model_version, config_version и режимы, прошедшие приемку. Ограничения OCR и заполнения отражаются в capabilities и документации поставки.

До начала испытания B08 нужны записи с реальной точки, известная геометрия прохода и максимальная скорость мешков. До B09 — проверка видимости номера и двери. До объемного режима B10 — система отсчета угла, размеры вагона, калибровка и эталон измерения. До B13 — контракт ERP. Эти данные не мешают последовательно реализовать B00–B06 и ручную идентификацию.
